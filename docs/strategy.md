# Стратегия развития модели
 
> Черновик. Цифры в разделе про объёмы это ориентиры, перед сдачей добавить источники (документация PostgreSQL, технические статьи) и сверить названия таблиц с итоговой моделью.
 
## 1. Какие сущности добавятся
 
### Возвраты и отмены
- **Зачем:** сейчас видно только статус заказа, а причины и суммы возврата неизвестны.
- **Что добавится:** факт возврата (одна строка = один возврат по позиции заказа).
### Доставка
- **Зачем:** в данных есть только две даты (передан в доставку и вручён). Для анализа задержек нужны этапы пути заказа.
- **Что добавится:** факт событий доставки (одна строка = одно событие заказа) и справочник перевозчиков.
### Цены и акции
- **Зачем:** цена в позиции это цена на момент покупки, а скидки и акции не видны.
- **Что добавится:** справочник акций и история цен товара.
### Календарь и география
- **Зачем:** удобные срезы по месяцам, неделям, праздникам и регионам. Сейчас месяцы без заказов приходится получать календарной последовательностью в запросе.
- **Что добавится:** справочник дат и справочник регионов вместо текстовых колонок «город» и «штат».
## 2. Где понадобится историчность
Сейчас в `core` хранится только последнее состояние справочников. Это теряет прошлое:
- **Адрес продавца и покупателя:** если он поменялся, старые заказы покажут новый адрес, и отчёты по регионам изменятся задним числом.
- **Категория и характеристики товара:** при смене категории выручка прошлых периодов «переедет» в новую.
- **Статус заказа:** хранится только итоговое значение, а путь заказа (оформлен, оплачен, отгружен) не виден.
- **Решение:** для таких справочников хранить версии записей с датами «действует с» и «действует по» (медленно меняющиеся измерения, SCD тип 2), а статусы заказов писать отдельной таблицей событий.
## 3. Что упрётся первым при росте объёма
1. **Полная пересборка `core` при каждой загрузке.** Скрипт пересоздаёт всё с нуля, и при росте данных это станет медленным. Нужна инкрементальная загрузка: обрабатывать только новые и изменившиеся строки.
2. **Таблица позиций заказов.** Она самая большая, и на ней строятся почти все отчёты. Решения: индексы по датам и ключам, разбиение таблицы на партиции по месяцам.
3. **Тяжёлые аналитические запросы на той же базе, куда пишутся данные.** Отчёты начнут мешать загрузке. Решение: заранее посчитанные витрины в схеме `mart`.
4. **Качество данных.** С ростом числа источников растёт число расхождений. Сейчас есть 16 проверок (число строк, уникальность ключей, связи, суммы). При росте их нужно запускать автоматически после каждой загрузки и останавливать загрузку при провале.
## 4. Технологический стек
 
### Сколько хватает PostgreSQL
- **До нескольких сотен миллионов строк:** обычный PostgreSQL на одном сервере справляется для аналитики, если есть индексы и партиционирование.
- **Порядок миллиардов строк и тяжёлые запросы по всей истории:** PostgreSQL начинает упираться в скорость чтения данных, потому что хранит строки целиком, а аналитике нужны отдельные колонки.
- Сейчас у нас около 550 тысяч строк, то есть запас в тысячи раз.
- **Источники:** добавить перед сдачей.
### Что идёт следом
- **Колоночное хранилище** (например, ClickHouse): быстро читает отдельные колонки, хорошо сжимает данные, подходит для отчётов по большим объёмам.
- **Облачное хранилище данных** (например, BigQuery или Snowflake): не нужно администрировать серверы, мощность растёт по запросу, но платить придётся за объём и запросы.
- **Почему именно так:** аналитические запросы читают много строк, но мало колонок, и колоночный формат под них устроен лучше. PostgreSQL остаётся для рабочих систем и небольших витрин.
### Инструменты вокруг
- **dbt:** управление SQL-моделями, тестами и документацией (наши 16 проверок естественно превращаются в тесты).
- **Планировщик (например, Airflow):** запуск загрузки по расписанию и контроль ошибок.
## 5. Этапы перехода и риски
1. **Сейчас:** PostgreSQL, пересборка скриптом, проверки после загрузки.
2. **Первый этап роста:** инкрементальная загрузка, партиции, справочник дат, SCD для справочников.
3. **Второй этап:** перенос тяжёлых отчётов в колоночное хранилище, PostgreSQL остаётся источником.
4. **Риски:** расхождение цифр между старой и новой системами (сверять параллельно на одних данных), потеря истории при переносе, рост затрат на поддержку нескольких систем.
