# Записка о решениях

## 1. Что считаем выручкой и как

### Выручка
- **Выбрали:** сумма `price` по позициям заказов со статусом `delivered`, без стоимости доставки.
- **Отказались от:** учёта всех статусов и включения доставки.
- **Почему:** отменённые и недошедшие заказы деньгами не стали, доставка не доход продавца. Итог 13 221 498,11 совпал с контрольным.

### Месяц заказа
- **Выбрали:** месяц оформления (`purchase_at`).
- **Отказались от:** месяца вручения.
- **Почему:** дата оформления есть у всех заказов, а дата вручения пуста у недоставленных.

### Месяц без заказов
- **Выбрали:** календарная последовательность месяцев, в отчёте 24 строки, один месяц с нулевой выручкой.
- **Отказались от:** отчёта только по месяцам, в которых есть заказы.
- **Почему:** иначе месяц пропадает из отчёта.

### Средний чек
- **Выбрали:** сумма `price` + `freight_value` по заказу, затем среднее по доставленным заказам (159,88).
- **Отказались от:** среднего по позициям.
- **Почему:** чек это свойство заказа целиком. Среднее по позициям даёт неверные 123,75 и 139,97.
- **Заметка для защиты:** выручка считается без доставки, а чек с доставкой. Выручка продавца это цена его товаров, чек это сколько заплатил покупатель за заказ.

### Выручка продавца
- **Выбрали:** считаем только по позициям самого продавца.
- **Отказались от:** суммы заказа целиком.
- **Почему:** в одном заказе могут быть товары разных продавцов, иначе деньги посчитаются дважды. У топ-продавца 226 987,93.

## 2. Ключи и гранулярность

### Ключ покупателя
- **Выбрали:** `customer_unique_id`.
- **Отказались от:** `customer_id`.
- **Почему:** `customer_id` выдаётся заново на каждый заказ. Уникальных людей 96 096, а не 99 441. Повторных покупателей 2 997 (3,12%).
- *Ждёт подтверждения от `sql-core`.*

### Гранулярность фактов
- **Выбрали:** заказ, позиция и платёж хранятся раздельно.
- **Отказались от:** одной широкой таблицы.
- **Почему:** при объединении разных уровней суммы задваиваются.
- *Ждёт подтверждения от `sql-core`.*

### Отзывы
- **Выбрали:** не используем `review_id` как единственный ключ, строки не удаляем.
- **Отказались от:** первичного ключа по одному `review_id` и удаления повторов.
- **Почему:** один `review_id` встречается у разных заказов (814 лишних вхождений из 99 224 строк).
- *Итоговый ключ ждёт решения от `sql-core`.*

## 3. Пропуски и аномалии

### Товары без категории (610)
- **Выбрали:** отдельная категория `Unknown`. Если у категории нет перевода (таких 2), сохраняем исходное португальское название.
- **Отказались от:** удаления таких товаров и значения `NULL`.
- **Почему:** не теряем их выручку, сумма по категориям сходится с общей (74 категории).

### Заказы без позиций (775) и без отзывов (768)
- **Выбрали:** сохраняем в `core`.
- **Отказались от:** `INNER JOIN` с позициями и отзывами.
- **Почему:** `INNER JOIN` молча терял бы эти строки.

### Аномалии дат (8 delivered без даты вручения, 6 недоставленных с датой)
- **Выбрали:** переносим как есть и отмечаем.
- **Отказались от:** исправления и удаления.
- **Почему:** сырые данные не правим, причину мы не знаем.

## 4. Как убедились, что ничего не потеряли
- Подготовлено 16 SQL-проверок: число строк в основных таблицах, уникальность ключей, отсутствие позиций без заказа и товара, платежей без заказа, контроль общей выручки и сверка денежных сумм позиций с исходными данными.
- По отчёту автора проверок, все 16 прошли в локальном тестировании.
- Связи между позициями, заказами, товарами, продавцами и платежами нарушений не показали.
